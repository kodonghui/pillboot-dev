# 실행 2026-11-05 웹 버그·UX와 영상 흐름 걷기(DEC-034)

- 왜: PM 프롬프트 '버그·UX(DEC-034)'의 6번 "영상 시나리오 흐름(사진 등록 → 같이 먹어도 되는지 → 일정 → 달력 → 알림)을 웹에서 직접 걸어 보고 어색한 문구·막히는 곳을 고침. 찾은 것과 고친 것을 docs/12-qa/runs에 기록함."(2026-11-04 프로젝트 대화)에 따름.
- 화면정의서: [v3-dec-034-web-ux.md](../../../react-client/design/v3-dec-034-web-ux.md)
- 환경: 이 브랜치 화면을 Vite 개발 서버로 띄우고 **가짜 API**(가상 인물·가상 약, 저장소에 넣지 않음)에 붙여 앱 안 브라우저 창에서 375×812와 1280×800으로 걸음. 서버 코드는 바꾸지 않음.
- 왜 가짜 API인가: 실제 키는 운영 서버 운영 설정에만 있음. 임시 서버를 띄우려고 운영 설정을 읽으려 했으나 권한에서 막혀 우회하지 않고 접음. 운영 공개 사이트에는 내가 로그인·가입하지 않음. 그래서 **실제 사진 판독·실제 AI 답·실제 공공데이터·실제 알림은 이번에 보지 않음**(아래 '보지 못한 것').

## 찾아서 고친 것

| 찾은 것 | 고침 | 확인 |
| --- | --- | --- |
| 약 저장 안내에 다음 할 일이 일정뿐이라 영상의 '같이 먹어도 되는지'로 이어지지 않음 | `같이 먹어도 되는지 묻기` 버튼 추가 | 375에서 두 버튼 44px, 두 줄로 내려감, 문서 폭 375 |
| 일정 저장 뒤 목록으로 말없이 돌아옴 | `일정을 저장했어요.`와 `복용 달력 보기` | `/calendar?month=2026-11`로 잇는 것을 링크 값으로 봄. 1280에서 안내 높이 78px |

## DEC-034 1~5 확인

모두 가짜 API에서 봄. 근거는 브라우저 안에서 잰 값과 글임.

| 항목 | 확인한 것 |
| --- | --- |
| 1 시작 화면 | 업데이트 기록 묶음이 없고 강점 두 칸이 보임(1280 두 칸, 375 한 칸). 바닥 줄 `업데이트 기록` 링크 44px, 문서 폭 넘침 없음 |
| 2 마이크를 못 쓸 때 | 권한 거절(`NotAllowedError`)과 그 밖의 실패(`NotFoundError`) 둘 다 `약봉이에게 글로 말하기`가 나옴. 누르면 창이 닫히고 그 프로필의 새 대화로 가며 입력창에 보던 약 이름이 들어가고 예시 안내가 보임 |
| 3 구슬 아래 안내 | `말로도 일정을 등록할 수 있어요`가 375에서 한 줄, 1280에서도 보임 |
| 4 약별 복용 기간 | 프로필별 묶음, 시작일 늦은 순, 끝난 일정 포함. 줄을 누르면 그 달로 가서 상세가 열림. 일정이 없으면 안 보임은 코드로 봄 |
| 5 같은 약 | MED-03 줄과 고른 약 안내, IMG-04 후보, SCH-03 주의 안내에서 일정 화면으로 가는 링크 값을 봄 |

MED-03에서 저장이 409로 돌아오면 그 후보가 이미 등록으로 바뀌고, 약 목록을 다시 읽어 줄과 안내 두 곳에 `일정 고치기`가 나오는 것도 봄.

## Codex 리뷰로 고친 것

| 찾은 것 | 고침 | 확인 |
| --- | --- | --- |
| SCH-03에서 다른 사람을 골라 `지금 일정 고치기`로 가면 돌아올 때 약 상세가 관리할 사람 기준이라 찾지 못함 | 다른 사람이면 달력으로 돌아옴 | 링크 값: 같은 사람 `from=drug`, 다른 사람 `from=calendar`. 저장 뒤 돌아가는 것까지 누르지는 않음 |
| 대화방 만들기가 느릴 때 창을 닫아도 늦은 응답이 화면을 옮김 | 닫기·다시 시작·일정 상세·화면 떠남에서 요청을 무효로 함. 관리할 사람도 넘어갈 때만 바꿈 | 응답을 1.5초 늦춰 봄: 닫으면 달력에 남고, 두 번 눌러도 대화방은 하나만 생김. 창이 안 보여 `close` 이벤트는 직접 보내 시험함(크롬은 그릴 때 보냄). 화면을 떠나는 경우와 다시 시작은 코드로 봄 |

## 보지 못한 것

- 실제 처방전 사진 판독, 실제 AI 답(같이 먹어도 되는지), 실제 공공데이터. API로는 [2026-11-04-stage-api.md](2026-11-04-stage-api.md)에서 봄.
- 실제 크롬의 복약 알림 수신. 앱 안 브라우저는 알림이 막혀 있음.
- IMG-05 낱알 후보의 링크: 가짜 응답을 만들지 않아 화면으로 보지 않음. 코드로만 봄.
- 약별 복용 기간 '다시 시도'를 눌러 복구되는 것, 실패 안내의 화면 모양: 약 목록 실패로 달력이 깨지지 않는 것만 봄.
- 음성 대화가 실제로 이어지는 경우.
- 스크린 리더, 360px 폭.

촬영 전에 PM 데모 계정으로 공개 사이트에서 같은 흐름을 한 번 걸어 봐야 함.

## PM에게 여쭐 것: 한 약에 일정 두 개

지금은 이미 있는 약이면 그 일정 고치기로 잇는 것까지 했음. 한 약에 일정을 둘 두려면 스키마를 바꿔야 함. 아래는 CT 안이며 정해지지 않았음.

| 안 | 내용 | 영향 |
| --- | --- | --- |
| A. 고치지 않음(권고) | 약 하나에 일정 하나를 유지함 | 없음. 발표 뒤 다시 봄 |
| B. 일정 표를 나눔 | `my_drug`에서 시작일·끝일·복용 시각·1회 개수·복용 때를 새 자식 표로 옮김. 과거 일정 이력도 남길 수 있음 | 가장 넓음. `MyDrug`, `MyDrugService`, `ScheduleProposalService`, `MedicationLiveTargetResolver`, `MedicationReminderRepository`, 달력 `scheduleKey`, 화면 `DrugPicker`·`ScheduleNewPage`, JSON 계약. 운영 DB 이관 필요 |
| C. 유일 제약을 넓힘 | `uk_my_drug_profile_item`을 (profile_id, item_seq, start_date)로 넓혀 같은 약 행을 여럿 둠 | B보다 작지만 약 목록에 같은 약이 여러 줄이 되고, V3-REQ-50과 '이미 등록함' 규칙, 대화·카톡 대상 찾기를 다시 정해야 함 |

- SQL 번호: 18·19는 4차 진료 일정이 씀. 안을 고르면 20번 이후를 씀. 적용 전 다른 스레드와 번호를 다시 맞춤.
- 권고 이유: 시연 흐름에 두 일정이 필요하지 않고, B·C 모두 알림·대화·달력을 함께 건드려 발표 직전 위험이 큼. 반대 근거: 실제 사용자는 약을 끊었다 다시 먹거나 용량을 바꿀 수 있어 이력이 남지 않는 것이 아쉬울 수 있음.
