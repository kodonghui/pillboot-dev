# 필받음 v3 기능 명세

- 상태: 초안(2026-11-02). 입력은 [v3 요구사항](../02-prd/requirements-v3.md) V3-REQ-33~80, [v3 사용자 흐름](../03-user-flow/user-flow-v3.md) V3-FL-17~29, [도메인 용어집](../01-domain/domain.md) TERM-001~018, 결정 DEC-001~014. 2026-11-04 PM 요청으로 대화 속 알약 사진(V3-REQ-81~84, V3-FL-30, V3-CHAT-009·010, V3-KAKAO-011)을 더했고 이 행들은 PM 결정(9.1 Q1~Q5) 전이라 '결정 대기'임.
- 기존 영역별 명세(AUTH·PROF·REG·DRUG·SCHED·DOSE·NOTI·CHAT·COMMON·V2-*)는 Notion 기능 원장이 원본이며 여기서 고치지 않음. v3가 바꾸는 기존 행은 7장에 적음(REG-003 포함).
- 코드 사실은 2026-11-02 팀 저장소 `docs/v3-scope-20261102` 브랜치(기준 `9b5b5ef`)에서 확인함. API 경로·테이블 이름은 06 API·05 ERD에서 정하며, 이 문서의 이름은 후보임.
- 수용 기준은 "~이 주어지고, ~하면, ~임" 순서로 씀.

### 8.4 V3-CHAT-007 일정 해석

기존 단문 일정 해석기(`MedicationVoiceInterpreter`)를 '해석만' 쓰고 저장은 확정 뒤에 함. 입력·출력 형식은 기존 `ParsedCommand`와 같고, 권한·업무 검사도 그대로 씀. 아래 표의 대상 약·기본값·확정 규칙은 TASK-029 구현에서 정함(DEC-019, 2026-11-03).

| 항목 | 내용 |
| --- | --- |
| 대상 약 | 의도 가르기(8.1)가 고른 약목록 이름과 같은 약이 그 프로필에 하나일 때만 씀. 직접 입력한 약도 이름으로 고를 수 있음. 이름이 없거나 같은 이름이 둘 이상이면 해석기를 부르지 않고 어느 약인지 물음 |
| 입력 | 질문 글, 오늘(한국 날짜), 고른 약 하나(약목록 번호·이름·프로필 관계 값) |
| 보내지 않는 것 | 프로필 이름(대상은 서버가 이미 정함), 다른 약·프로필, 대화 기록, 회원 정보 |
| 말하지 않은 값 | 일정을 바꾸는 요청이라 지금 일정을 그대로 둠. 기간만 말하면 오늘부터 셈. 하루 횟수만 말하면 기본 시각(07:00·11:00·17:00)을 앞에서부터 쓰고, 지금 횟수와 같으면 지금 시각을 둠. 일정이 없는 약은 기존 단문 일정 명령의 기본값(오늘 하루, 기본 시각 셋)을 씀. 기존 명령의 기본값(화면에서 고른 날짜 하루)을 그대로 쓰면 "한 알로 바꿔 줘"가 한 달 일정을 하루로 줄여서 바꿈 |
| 서버가 확인하는 것 | 일정 저장 규칙과 같음(시각 `HH:mm` 하루 1~3개·중복 없음, 1회 개수 1~10, 복용 때 20자 이하, 시작일 ≤ 종료일, 종료일과 기간이 맞음). 규칙 밖이면 카드 없이 그 값을 다시 말해 달라고 안내함. 바뀐 뒤가 지금과 같으면 같다고 안내함 |
| 실패 | 해석기 오류·시간 초과(20초, 질문 전체 한도 안) → 일정을 읽지 못했다고 안내하고 카드를 만들지 않음. 삭제·그만 먹기처럼 바꾸기가 아닌 요청 → 바꿀 값을 말해 달라고 하고 그만두기·지우기는 복용 달력으로 안내함 |
| 카드 | '지금'은 만들 때의 대상 약 일정, '바뀐 뒤'는 위 규칙으로 만든 일정이고 제안 표의 JSON 칸에 같은 모양(openapi-v3 `ScheduleValues`)으로 둠. 약 이름은 약목록의 지금 이름이고 약을 지우면 비어 있음. 지금 1회 개수가 확인되지 않았으면 '지금' 개수는 비어 있고(내 약 응답과 같음), 개수를 말하지 않았으면 '바뀐 뒤'는 저장된 값을 씀(TASK-031, DEC-019) |
| 확정 | 대상 약 행을 잠그고 지금 일정을 카드의 '지금'과 값으로 맞춰 봄(1회 개수는 확인 여부까지). 다르거나 약을 지웠으면 409 `SCHEDULE_CHANGED`이고 카드는 대기 그대로이며 아무것도 저장하지 않음. 같으면 기존 일정 저장(전체 교체)으로 '바뀐 뒤'를 저장함. 1회 개수를 저장하므로 확인되지 않았던 1회 개수도 확인됨으로 바뀜(기존 일정 저장과 같음) |
| 사람 결정 | 회원(지인)이 카드로 확정해야만 일정이 바뀜 |

### 8.5 V3-CHAT-009·V3-KAKAO-011 알약 사진 판독(결정 대기)

웹 약 등록의 알약 사진 판독(REG-007, `PillOcrRules`, 정식 경로 `PhotoIdentificationWorkflow`의 `PILL`)을 그대로 쓰는 안을 적음. 바뀌는 것은 결과를 등록 제안으로 받는 것과 상담방 시간 한도 안에서 도는 것뿐임. 사진 종류를 AI가 가르는 안(Q1 B안)을 고르면 그 호출은 새로 정함.

| 항목 | 내용 |
| --- | --- |
| 입력 | 알약 사진. 지금 정식 경로는 앞·뒤 2장만 받고(호환 경로는 1~2장), 1장을 받을지는 9.1 Q2. 사진 순서는 공식 앞·뒤를 뜻하지 않고 두 방향으로 비교함 |
| 모델 | `OPENAI_VISION_MODEL`과 공통 `OPENAI_REASONING_EFFORT`. 정식 경로는 두 장을 한 번에 보내 호출 1번임. 처방전 판독은 다른 모델(`OPENAI_PRESCRIPTION_MODEL`, 기본 `gpt-6-luna`, `max`)을 씀. 운영 서버의 실제 모델 값은 서버 `.env`에 있어 이 문서에서 확인하지 않음 |
| 보내지 않는 것 | 회원·프로필 정보, 대화 기록 |
| 출력 | 알약이 한 알인지(`singlePill`), 면마다 각인과 상태(READABLE·NONE·UNREADABLE), 분할선, 모양, 색, 선명할 때만 제품명·제약사. 품목코드는 만들지 않음 |
| 서버가 확인하는 것 | 판독 전: 프로필 권한, 식별 켜짐·식별 DB 패치, 낱알 목록 준비. 하나라도 아니면 유료 판독을 부르지 않음. 판독 뒤: 각인이 읽힌 면 1개 이상, 모양·색이 낱알 목록에 있는 값인지(아니면 `UNREADABLE`과 빠진 단서). 후보는 각인·분할선이 맞는 순서이고 최대 5개, 전체 수는 따로 셈 |
| 시간 | 낱알 한도 `PILL_TIMEOUT_MS` 기본 85초(판독과 대조를 합친 시간), 상담방 사진 전체 한도 88초 안. 처방전 판독 한도는 60초. 알약 판독 시간은 아직 잰 적 없음(처방전 판독은 2026-11-04 QA TC-114에서 8.2초). 카톡 목표는 V3-REQ-63의 P95 60초 |
| 남기지 않는 것 | 사진은 처리 뒤 바로 지움(V3-CHAT-006과 같음). 읽은 단서를 카드에 남길지는 9.1 Q3 |
| 실패 | V3-CHAT-009 예외 칸 |
| 사람 결정 | 회원(지인)이 카드·빠른 답장으로 확정해야만 약목록에 저장됨 |

### 9.1 대화 속 알약 사진 · PM 결정 대기(2026-11-04)

PM 말씀(2026-11-04): "이거 채팅에서 낱알가지고는 검색못하나? 홈페이지랑 카톡에서".

지금 사실(2026-11-04 `develop` `d8d4b42`, 카톡 다리 `main`에서 확인함):

- 웹 상담방과 카톡 다리는 모두 `POST /api/chat-sessions/{sessionId}/photos`로 사진 1장을 보냄. `PhotoProposalService`는 늘 `ImagePhotoKind.PRESCRIPTION`·사진 1장으로 판독해서, 알약 사진은 '약 이름을 읽지 못함'(다시 찍기 안내)으로 끝남.
- 알약 식별은 웹 약 등록의 IMG-02 알약 사진 올리기에만 있음. 앞·뒤 2장, 식약처 낱알식별 목록, 판독 지시 `PillOcrRules`, 한도 85초, 후보 최대 5개이고 6개 이상이면 고르지 못하게 함.
- 다리는 사진만 온 묶음을 마지막 사진 뒤 3초까지 기다리고, 한 묶음에 사진이 둘 이상이면 서버를 부르지 않고 '한 장씩 보내 주세요'라고 답함. 사진 스위치는 켜짐, 음성은 꺼짐.

아래 Q1~Q5는 PM이 정할 것임. 'CT 추천'은 추천일 뿐 정한 것이 아님. 정한 뒤 DEC 번호와 PM 말씀을 붙이고, V3-REQ-81~84·V3-FL-30·V3-CHAT-009·010·V3-KAKAO-011의 상태를 바꾸고 목업·06 API·WBS로 넘어감. 화면 쪽 안(카드·문구)은 [화면 정의](../../react-client/design/v3-chat-pill-photo.md)에 자세히 있음.

#### Q4 못 찾았을 때 문구

- 화면 정의 '고를 것 3'에 웹·카톡 문구 초안이 있음(단서 못 읽음·한 알이 아님·맞는 약 없음·후보 6개 이상·장애·잘못 고른 종류).
- PM이 볼 것: 문구를 그대로 쓸지, 웹 답변에 약 등록의 알약 사진 화면(IMG-02, 단서를 직접 고치는 '단서 보완하기'가 있음)으로 가는 버튼을 둘지.
- CT 추천: 버튼 없이 글 안내만 둠. 대화에서 보낸 사진은 처리 뒤 바로 지워져 그 화면에 넘길 수 없어 다시 찍어야 하고, 카톡 지인은 웹 로그인이 없음. 반론: 단서 보완은 웹 화면에만 있어 각인이 살짝 틀린 경우를 대화에서는 고칠 수 없음.
