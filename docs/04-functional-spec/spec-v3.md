# 필받음 v3 기능 명세

- 상태: 초안(2026-11-02). 입력은 [v3 요구사항](../02-prd/requirements-v3.md) V3-REQ-33~80, [v3 사용자 흐름](../03-user-flow/user-flow-v3.md) V3-FL-17~29, [도메인 용어집](../01-domain/domain.md) TERM-001~018, 결정 DEC-001~014. 2026-11-04 PM 요청으로 대화 속 알약 사진(V3-REQ-81~84, V3-FL-30, V3-CHAT-009·010, V3-KAKAO-011)을 더했고 같은 날 PM이 9.1 Q1~Q5와 카톡 두 장 모으기를 정해(DEC-030) 이 행들은 '초안'임. 사진 종류 가르기(Q1 B′)는 만들기 전에 시험함. 같은 날 PM 질문으로 카카오톡 약봉이와 웹 계정 연결(V3-REQ-85~92, V3-FL-31·32, V3-KAKAO-012~016)을 더했고, 같은 날 PM이 9.2를 정해(DEC-029) 이 행들은 '초안'임.
- 기존 영역별 명세(AUTH·PROF·REG·DRUG·SCHED·DOSE·NOTI·CHAT·COMMON·V2-*)는 Notion 기능 원장이 원본이며 여기서 고치지 않음. v3가 바꾸는 기존 행은 7장에 적음(REG-003 포함).
- 코드 사실은 2026-11-02 팀 저장소 `docs/v3-scope-20261102` 브랜치(기준 `9b5b5ef`)에서 확인함. API 경로·테이블 이름은 06 API·05 ERD에서 정하며, 이 문서의 이름은 후보임.
- 수용 기준은 "~이 주어지고, ~하면, ~임" 순서로 씀.

### 8.6 V3-COMMON-005 AI 모델과 Claude 백업

PM 말씀 "그리고 소네트 5.5 미디엄, 테라 6.1 미디엄으로 설정해줘. 웹이던 카카오던"과 'Terra 기본, Sonnet 백업' 선택(DEC-028)을 따름. 기존 AI 호출(8.1~8.5, 답변·요약·일정 해석)의 입력·출력·서버 확인·사람 결정은 바꾸지 않고, 부르는 모델과 실패했을 때의 길만 바꿈.

| 항목 | 내용 |

| 기본 모델 | OpenAI `gpt-6.1-terra`. 답변·요약·의도·일정 해석(`OPENAI_CHAT_MODEL`), 알약 판독(`OPENAI_VISION_MODEL`), 처방전 판독(`OPENAI_PRESCRIPTION_MODEL`)에 씀. effort는 `OPENAI_REASONING_EFFORT`·`OPENAI_CHAT_REASONING_EFFORT`·`OPENAI_PRESCRIPTION_REASONING_EFFORT` 모두 `medium`. 질문 분류(Decisions API, `OPENAI_DECISION_MODEL`)는 그 API가 받는 모델일 때만 바꾸고, 받지 않으면 지금 모델을 둠 |

| 보내지 않는 것 | 8.1~8.5와 같음. |
| 남기는 것 | 로그에 백업 사용 여부, OpenAI 실패 종류(예외 종류·상태 코드), Claude 모델·토큰 수·걸린 시간. 키·질문·사진·답 원문은 남기지 않음 |
| 실패 | Claude도 실패하면(키 거절·한도·서버 오류·시간 초과·거절·형식 오류) 처음 OpenAI 실패를 그대로 올려 지금과 같은 503 문구가 나옴 |
| 바꾸지 않는 것 | 기존 JSON 계약, DB, 화면, 카톡 다리. 모델 이름·effort는 서버 설정에서 바꿈(웹: `<서버 설정 파일>`와 게이트웨이, 카톡: `<배포 경로>`). 웹 설정의 `OPENAI_API_KEY`는 게이트웨이 통행 토큰이라 OpenAI 키로 바꾸지 않음 |

##### Q1 B′ Decisions로 가르기(DEC-030으로 정함, 2026-11-04)

PM 질문 "Q1. descision api 사용하는건 어때?"에 따라 B안을 OpenAI Decisions API로 하는 안을 살핌.

확인한 사실:

- 서버는 이미 질문 분류(`QuestionClassifier`)에 Decisions API를 씀. `OpenAiClient.createChoice` → `POST /decisions`, 모델은 설정 `openai.model.decision`, 짧은 클라이언트이고 재시도하지 않으며 실패하면 Claude 백업(`ClaudeBackupClient.choice`)을 씀. 지금 이 경로는 글만 받음(코드 확인).
- 사진은 이미 같은 제공자에게 data URL로 보내 판독함(`createJsonFromImages`, OpenAI가 실패하면 Claude). 종류 가르기를 더해도 사진을 받는 곳이 늘지 않음.
- OpenAI 문서(2026-11-04 확인, [Decisions 안내](https://developers.openai.com/api/docs/guides/decisions)·[Create a decision](https://developers.openai.com/api/reference/resources/decisions/methods/create)): 입력에 사진(`input_image`, HTTP(S) 주소나 base64 data URL, `file_id`는 안 됨)을 넣을 수 있음. 모델은 gpt-6-luna 하나임. 값은 캐시하지 않은 입력 100만 토큰당 0.10달러이고 출력은 받지 않음. choice 답에 `probabilities`·`confidence`가 옴. Responses API보다 10배쯤 빠르다고 적혀 있음. 사진으로 choice를 고르는 공식 예시는 없음.
- 카톡 빠른 답장은 PC·휴대폰 모두 보이지 않음(PM 휴대폰 확인 "3. 안보여", `v3-kakao-web-link.md`). A안의 카톡 묻기는 회원이 '처방전'·'알약'을 글로 보내야 함.

| 자리 | 동작 |
| --- | --- |
| 가르기 | 사진이 오면 판독 전에 Decisions choice 한 번. 고를 값은 `PRESCRIPTION`(처방전·약봉투)·`PILL`(알약)·`OTHER`. 답의 값과 `confidence`만 씀 |
| 애매할 때 | `OTHER`이거나 확신이 기준보다 낮으면 판독하지 않고 종류를 물음. 웹은 답변 안 버튼 두 개, 카톡은 '처방전' 또는 '알약'을 글로 보내게 함(DEC-027 글로 고르기). 기준 값은 시험 뒤 정함 |
| 두 장(Q2 A) | 카톡 한 묶음에 사진이 둘이면 장마다 가름. 둘 다 `PILL`이면 앞·뒤 한 쌍으로 판독함. 처방전이 섞이면 지금처럼 한 장씩 보내 달라고 함 |
| 백업 | OpenAI가 실패하면 Claude로 같은 고르기를 함. 지금 Claude 백업 choice는 글만 받아 사진용을 새로 만듦. 둘 다 실패하면 종류를 물음 |
| 남기지 않음 | 가르기 결과는 사진과 함께 판독 뒤 버림. 로그에는 값·확신·걸린 시간만 남김 |

- 장점: 웹·카톡 모두 회원이 한 번 더 고르지 않음. 카톡에서 보이지 않는 빠른 답장에 기대지 않음. 이미 쓰는 클라이언트·백업 틀을 다시 씀. 값이 작음(출력 없음).
- 단점: 사진마다 AI 호출이 1번 늘어 판독 앞에 시간이 더해짐(잰 적 없음). 사진 가르기 정확도도 잰 적 없음. 새 지시·Claude 사진 choice·시험이 필요해 A안보다 일이 많음. 높은 확신으로 틀리면(처방전을 알약으로) B안처럼 엉뚱한 안내가 나옴.
- 시험(만들기 전): 처방전·약봉투·알약 앞·뒤·그 밖 사진으로 Decisions 가르기의 정확도·확신·걸린 시간을 잼. 처방전·약봉투는 개인정보를 가린 사진만 쓰고 저장소에 올리지 않음. 결과로 확신 기준을 정해 PM에게 드림.
- 정함: B′(DEC-030, PM "추천대로 진행"). CT 추천(바뀜): B′. 카톡 빠른 답장이 보이지 않는다는 휴대폰 확인으로 A안의 카톡 쪽 부담이 커짐. 시험에서 잘못 가르는 경우가 기준보다 많으면 A안으로 돌아감. 반론: 시험·백업 일이 늘고 정확도가 아직 근거 없음.

- 카톡 다리(`카톡 다리.service`)는 같은 서버의 다른 필받음 서버 `카톡용 서비스`(`<배포 경로>`, 127.0.0.1:18080, 고정 커밋 `453fc3d`)를 부르고 DB는 `pilldb`임. 운영 계정 `yakbong@pillbadeum.local` 하나로 로그인하고, 카카오 사용자마다 그 계정 아래 `OTHER` 자동 프로필을 만들거나(V3-KAKAO-001·002) 운영자가 `admin link`로 이음.
- 그래서 웹 회원의 약은 카톡에서 보이지 않고, 카톡 상담은 웹에 나오지 않음. 두 서버는 회원·프로필·상담방 번호도 따로 매김.
- 다리 연결 기록(개수만 읽음): 말을 건 사람 1명, 연결 0명, 지우지 않은 옛 프로필 0개. 지금 옮겨야 할 카톡 기록은 없음.
- 웹 인증은 Bearer 액세스 토큰(JWT, 서명키 하나, 기본 10시간 `JWT_ACCESS_TOKEN_EXPIRATION`)뿐이고 refresh 토큰·서버 쪽 폐기·로그아웃 API가 없음([auth-logout.md](../../react-client/docs/auth-logout.md)). 서버는 토큰 안의 회원 번호로 DB 조회 없이 인증하고, 내 데이터인지는 서비스가 확인함(`SecurityUtil.checkOwner`와 프로필 소유 확인). 그래서 지금 JWT를 다리에 오래 맡기는 방식은 끊을 수 없어 쓰지 않음.
- 카카오 봇 이벤트에는 카카오 로그인 사용자 ID가 없어 '카카오 로그인으로 자동 연결'은 v3 범위 밖임([요구사항](../02-prd/requirements-v3.md) 6장). 그래서 두 안 모두 회원이 한 번 직접 잇는 방식임.
- 다리에는 3차 전 연결 코드(다리가 만든 `ABCD-EFGH`를 운영자가 `admin link`로 잇던 것)를 읽는 코드가 남아 있음(`store.normalize_code`). A안은 방향이 반대임(웹이 만들고 사용자가 카톡에 보냄).

#### 코드 모양(A안)

- 서버가 `ABCDEFGHJKLMNPQRSTUVWXYZ23456789`(32자, 다리의 옛 코드와 같은 글자)에서 8자를 뽑고 숫자를 하나 이상 넣어 `7K3Q-M9XA`처럼 보임. 경우의 수는 약 1조(2^40)임.
- 다리는 웹 연결이 없는 사용자의 글이 앞뒤 공백을 빼고 `[A-Za-z2-9]{4}[- ]?[A-Za-z2-9]{4}`이고 숫자가 하나 이상이면 코드로 봄(소문자는 대문자로 바꿈). 첫 연결의 호칭 단계에서도 먼저 코드로 봄. 숫자 없는 영문 8자는 호칭으로 받음.
- 서버는 코드의 SHA-256 해시만 저장하고 원문은 코드 받기 응답에서 한 번만 보냄. 다리·서버 로그와 턴 기록에는 '코드 받음·맞음·틀림'만 남김.

#### 알리는 것과 동의(두 안 공통)

연결 전에 웹에서 아래를 보이고 확인란을 고르게 함. 연결 표에 동의 시각과 안내 판 번호를 남김.

- 연결하면 카카오톡 약봉이가 이 프로필(이름)의 약목록·복약 일정·출생연도·성별·임신 여부로 답함.
- 카톡에서 한 상담은 이 웹 계정의 상담 기록에 남고, 이 계정으로 로그인한 사람은 웹에서 볼 수 있음. 가족 프로필을 그 가족의 카톡에 이으면 그 가족의 질문이 계정 주인에게 보임. 카톡 연결됨 말풍선에도 같은 말을 적음.
- 카톡 대화는 카카오 서버를 거쳐 오가고, 휴대폰을 같이 쓰는 사람이 카톡 대화방에서 약 이름을 볼 수 있음.
- 카톡에서 확정한 약 등록·일정 바꾸기는 이 프로필에 바로 저장됨(확정 전에는 저장하지 않음, DEC-001).
- 카톡 복약 알림(DEC-033, DEC-013을 대신함): 켠 뒤에는 고른 프로필 약의 복용 시각에 카톡으로도 알림이 오고 카톡 `알림 끄기`로 끌 수 있음. 웹 푸시는 그대로 옴. 켜기 전까지는 '카톡으로 복약 알림은 보내지 않음' 안내를 그대로 둠(V3-KAKAO-018). 2026-11-06부터 카카오가 1:1 먼저 보내기를 막아, 카톡 알림은 웹 연결한 사람이 약봉이를 초대한 가족 단톡방으로 감(`react-client/design/v3-3-kakao.md` '가족 단톡방으로 보내기').
- 이 화면이나 카톡 `연결 끊기`로 언제든 끊을 수 있고, 끊어도 웹의 약목록·상담 기록은 지워지지 않음.
- 운영자: 웹 연결 회원의 기록은 약봉이 운영 계정이 아니라 회원 계정에 남음. 다리는 카카오 키·연결 종류·시각만 가짐(대화 내용을 다리에 두지 않는 지금 규칙 그대로).
- 확인할 것(법무 판단 아님): 가입 때 받은 '개인정보 수집 및 이용 동의'·민감정보 동의(`13_BASE_CONSENT.sql`)의 이용 목적에 카톡 전달이 들어가는지, 연결 동의를 약관 판으로 따로 관리해야 하는지.

#### 보안

두 안 공통:

- 남기지 않는 것: 연결 코드, 다리 키, HMAC 키, 연결 토큰, 승인 요청 확인 값, 카카오 사용자 키 원문. 다리 로그는 지금처럼 `#짧은키`만, 서버 로그는 연결 번호만 씀. 주소에는 B안 승인 요청 번호만 넣음(개인정보 없음, 10분·한 번).
- 저장: 코드·토큰은 SHA-256 해시로, 카카오 사용자 키는 다리 HMAC 값으로만 웹 DB에 둠(웹 DB에 카카오 키 원문이 없음). HMAC 키를 바꾸면 모든 웹 연결이 끊겨 다시 이어야 함.
- 범위: 다리로 부를 수 있는 API를 정한 목록(상담방 열기·질문·사진·음성·제안 읽기·확정·취소·내 약 읽기)과 연결된 프로필 하나(Q4 B안이면 그 회원의 프로필)로 막음. 프로필 만들기·지우기, 회원 정보, 약 직접 지우기, 일정 직접 저장은 다리로 부를 수 없음.
- 주소: 다리는 같은 서버 안의 127.0.0.1:18082로 부를 수 있으나, 공개 주소 요청도 앞단 프록시를 거쳐 127.0.0.1에서 들어옴. 그래서 주소로 다리를 가리지 않고, 프록시가 다리 인증 머리글을 지우거나 다리 API 경로를 공개 주소에서 막음(배포 때 확인, 9장).
- 제한: 코드 받기는 회원마다 10분에 5번, 틀린 코드는 카카오 사용자마다 5번이면 1시간, 서버 전체 코드 확인은 분당 상한(값은 06 API에서 정함).
- 비밀값은 다리 `.env`(600)와 웹 `<서버 설정 파일>`에만 두고 깃·채팅·노션·명령 출력에 넣지 않음(다리 README '지키는 것' 그대로). 넣을 때는 지금 `yakbong.sh token`처럼 값이 화면에 나오지 않게 함.

A안만:

- 다리 키는 32바이트 무작위 값이고 서버는 해시만 가짐. 두 개까지 받게 해 끊김 없이 바꿈.
- 코드 넘겨받기: 코드를 받은 다른 사람이 먼저 보내면 그 사람 카톡에 이 프로필 약이 보임. 화면에 '코드를 다른 사람에게 알려 주지 마세요'를 두고, 연결되면 PRF-04가 바로 '연결됨'과 연결 시각으로 바뀌어 회원이 알아챌 수 있게 함.

B안만:

- 승인 요청 번호는 다리가 만든 무작위 값(10분, 한 번)이고, 토큰을 받으려면 다리만 아는 확인 값(PKCE 방식)과 다리 비밀이 함께 있어야 함. 주소를 본 사람(링크 미리보기·방문 기록)은 토큰을 받지 못함.
- 연결 토큰은 32바이트 무작위 값이고 서버는 해시만 가짐. 지금 JWT와 다른 종류이며 서버가 요청마다 표에서 확인해 바로 끊을 수 있음.
- 채팅에서 받은 주소로 로그인하게 해 비슷한 가짜 주소에 속기 쉬워짐. 말풍선에 도메인을 적고 다른 주소에서는 로그인하지 말라고 알림.

#### `pilldb`에서 옮기기

- 지금 옮길 것: 2026-11-04 기준 연결 0명·지우지 않은 옛 프로필 0개라 옮길 카톡 기록이 없음. 다리 연결 기록(sqlite `links`)에는 종류(자동·웹) 칸을 더하고 B안은 암호화 토큰 칸을 더함. 지금 행이 없어 옮길 행도 없음.
- 앞으로 자동 프로필을 쓰던 지인이 웹에 연결하면 Q3대로 함(V3-KAKAO-016).
- 운영 계정과 자동 프로필을 어느 서버에 둘지는 Q2. Q2 B안이면 공개 웹 서버에 운영 계정을 새로 만들고(옮길 자동 프로필 0개) `카톡용 서비스`·`pilldb`는 백업 뒤 끔.
- 공개 웹 릴리스 `282b888`은 다리가 부르는 v3 API(등록·일정 제안, 사진 제안, 음성 받아쓰기)를 이미 가짐(다리 고정 커밋 `453fc3d`보다 새것). 다만 공개 웹을 올릴 때마다 다리도 영향을 받으므로 배포 전에 다리 시험을 같이 돌려야 함.

| V3-KAKAO-010 해제·삭제 | 운영자가 해제·삭제함 | 자동 프로필만. 웹 연결은 V3-KAKAO-015(회원이 끊음, 웹 기록은 남음) |

#### 정한 뒤 할 일(어림)

- 05 ERD: SQL 17 후보(연결 코드·연결 표, 또는 승인 요청·연결 토큰 표. Q5 B안이면 `chat_session` 경로 칸).
- 06 API: 이 절의 API 이름·오류 코드·제한 값. 기존 JSON 계약은 바꾸지 않고 더하기만 함.
- 목업: PRF-01 줄과 PRF-04(B안은 PRF-05도) 360·1280, 카톡 말풍선 360. 승인 전에는 화면·다리 코드를 고치지 않음(DEC-008).
- 구현과 시험 뒤 배포(웹 `app.env`에 다리 키 해시, 다리 `.env`에 키, 프록시 머리글 지우기). 서버 설정·배포는 이 문서 범위 밖이며 정한 뒤 따로 승인받음.

#### PM이 정할 것(정함: DEC-029, 위 '정한 것')

아래 Q1~Q6은 PM이 정함. 'CT 추천'은 추천일 뿐 정한 것이 아님. 정한 뒤 DEC 번호와 PM 말씀을 붙이고 V3-REQ-85~92·V3-FL-31·32·V3-KAKAO-012~016의 상태와 위 '바뀌는 것'을 고침.

##### Q1 어떻게 이을까

| 안 | 내용 |
| --- | --- |
| A 웹 코드 | 웹에서 받은 코드 8자를 카톡에 보냄. 서버가 연결을 갖고 다리는 다리 키 하나로 연결된 회원을 부름 |
| B 카톡 주소로 승인 | 카톡에서 받은 주소로 웹에 로그인해 승인함. 다리가 사람마다 연결 토큰을 보관함 |

- CT 추천: A안. 카톡 안 브라우저 로그인이 없어 부모님 또래도 따라 하기 쉽고, 다리가 사람마다 토큰을 쥐지 않으며, 다리에 코드 받는 자리가 이미 있음. 반론: 서버에 '다리 요청을 회원으로 바꾸는' 새 인증 길이 생겨 허용 목록·프로필 하나 제한을 빠짐없이 시험해야 함. B안은 표준 위임 토큰 방식이라 다리를 다른 서버로 옮겨도 그대로 쓸 수 있음.

##### Q2 웹 계정이 없는 지인은 어떻게 할까

| 안 | 내용 | 장단점 |
| --- | --- | --- |
| A 두 서버 그대로 | 웹 연결은 공개 웹 서버, 지인은 지금처럼 `pilldb` 자동 프로필 | 지인 쪽은 바뀌지 않음. 다리가 사람마다 서버를 골라야 하고 두 서버의 번호가 겹침. 서버 두 개를 계속 따로 올리고 백업함 |
| B 한 서버로 합침 | 운영 계정과 자동 프로필도 공개 웹 서버로 옮기고 `pilldb` 서버를 끔 | 서버·DB·백업이 하나이고 다리는 한 곳만 부름. 옮길 자동 프로필이 0개라 지금이 가장 쌈. 공개 웹에 운영 계정(설치 때 만든 무작위 20자 비밀번호)이 생겨 공개 로그인 화면에서도 로그인할 수 있게 되고, 공개 웹 배포가 카톡 지인에게도 바로 닿음 |
| C 웹 회원만 | 자동 프로필을 없애고 웹 가입·연결 방법만 안내 | 가장 단순하고 운영자 열람 문제가 없어짐. 가입이 어려운 지인은 카톡 약봉이를 못 씀. DEC-003·011·016과 V3-KAKAO-001·002·010을 고침 |

- CT 추천: B안. 반론: 공개 웹 서버 하나가 멈추면 웹과 카톡이 함께 멈추고, 웹 회원이 아닌 지인의 건강정보가 공개 웹 DB(운영 계정 아래)에 생김(지금 `pilldb`와 같은 성격).

##### Q3 자동 프로필로 쓰던 기록을 웹 연결 때 옮길까
